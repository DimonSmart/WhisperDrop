# IDD-0009.spec-push-to-talk-dictation

## Intent

ParakeetDrop supports background push-to-talk transcription into the already-focused editable control, without activating its own window. Recognition and insertion are independent: failed, skipped or unconfirmed insertion never discards recognized text.

## Related Specifications

- IDD-0001 — Local desktop transcription and session privacy
- IDD-0002 — Shared transcription queue and manual microphone capture
- IDD-0003 — Model availability
- IDD-0007 — AI post-processing, which is not automatic in dictation
- IDD-0008 — Native Parakeet Ultra runtime

## Behavior

- Windows x64 is the first supported background-dictation platform; macOS ARM64 follows with native status-item, hotkey and Accessibility implementations without duplicating session logic.
- On Windows, closing the main window hides it without ending the app. A tray icon offers Open, Enable/Disable Dictation, and Exit. Exit ends the process session and cleans temporary microphone recordings; hiding or reopening the window preserves history.
- Users can enable or disable dictation and change its hotkey in persisted settings. Default shortcut: Ctrl+Shift+Space. Shortcut conflicts with Windows or another application are reported rather than silently hijacked.
- The first physical press starts one capture. Repeated KeyDown events are ignored. Releasing the primary key or a required modifier stops capture. Missing key-up events, session lock and sleep must not allow infinite recording. Starting dictation during manual microphone recording is rejected.
- The recording indicator is mandatory. As soon as capture starts, show a visible small topmost overlay near a screen edge whether or not the main window is open. It does not activate a window, intercept keyboard input or accept pointer input. Hide it immediately on release/stop, even while recognition or insertion continues. There is no disable-indicator setting.
- Recording uses the existing microphone service. Releasing queues one session audio item and automatically transcribes it via Parakeet Ultra Q8_0 and the media-preparation pipeline; no streaming model, cloud recognition or automatic AI correction is used. A short accidental tap without usable audio does not create an empty result.
- Dictation items share the file/recording queue, preview, Copy, Copy raw, Copy all, retranscription, manual AI enhancement and Remove actions. Each item is marked Push-to-Talk and records capture interval, raw segments/result, recognition and insertion statuses. The history exists only in the process session.
- Recognition runs sequentially alongside ordinary file and microphone recordings. A second dictation can be captured while the previous one recognizes; it waits in the same scheduler. A successful recognition remains available for manual recovery even if insertion is skipped or fails.
- At key press record a short-lived identity of the focused editable control via accessibility APIs, including parent window and process. Before insertion confirm the original window/process/control remain active, editable, keyboard-focused, enabled and not a password field. Changing fields, switching applications, a destroyed/reloaded target or ambiguous identity skips insertion without focusing anything.
- Submit recognized Unicode text only once. Unicode and newlines are supported. On Windows use UI Automation for target identity and SendInput for non-activating submission; do not rewrite the clipboard or bypass elevation. Submitted means keystroke events were dispatched, not proof the application accepted them. Never mark Inserted without actual verification or retry automatically.
- Insertion statuses are NotRequested, Pending, Submitted, Inserted (only with proof), Skipped and Failed. Recognition and insertion errors have separate reasons. Retrying transcription from history does not retry previous insertion.
- Recording, model, accessibility and insertion errors do not crash the entire application. Finalized audio for failed recognition remains in the session queue for retry. Logs contain neither audio, transcripts nor key sequences.

## Product-Significant Architecture And Constraints

- Platform-specific tray/menu bar, hotkeys, overlay and target validation are isolated from shared recognition and session state.
- Windows WM_HOTKEY alone cannot track key release; monitor key state independently, including handling lost events.
- The focusless overlay is mandatory for every active background recording. A failed overlay initialization must not silently allow invisible listening.
- Existing recognition runtime serialization and the application's session queue remain authoritative; no second independent history or parallel recognizer.

## Non-Goals

- Streaming ASR, partial text insertion, always-on speech detection, persistent history, cloud services, automated AI correction, OS voice commands and automatic focus restoration.
- macOS implementation is a separate follow-on stage.

## Acceptance Criteria

- A Windows packaged app runs in tray with its window hidden, records from an external application while the hotkey is held, shows a mandatory topmost no-focus indicator, hides it on release, recognizes locally and submits Unicode only to a verified original editable control.
- Switching apps or controls, reloading a browser page, locking the session or targeting an elevated/password control never leads to unintended insertion. Audio and text remain recoverable after skipped or failed insertion.
- Rapid dictations remain independent queue items with sequential native recognition. Normal manual recording and file operations still work.
- Insertion status is independent; Submitted is never presented as confirmed insertion. Retranscription never implicitly inserts.
- Exit releases tray/overlay/hook and cleans temporary audio; hide/reopen preserves session. Hotkey settings survive restart.
- Real Windows x64 integration tests exercise Notepad, browser, editor, focus changes, Unicode, missing model/microphone and native Parakeet recognition.

## Verification

- Unit tests cover hotkey parsing, defaults and persistence, queue history metadata, no automatic AI, missing model and manual-retry semantics.
- Windows packaged-app testing must verify global keyboard hook, shortcut conflicts, non-focusing overlay and tray lifecycle, target identity and actual local model inference. CI compilation alone is not OS integration evidence.
