# IDD-0008.adr-whisper-decoding-fallback

## Status

Accepted — 2026-10-25

## Context

WhisperDrop (Whisper.net 1.9.1, whisper.cpp 1.8.5) exhibited catastrophic repetitive decoding on a long, predominantly Spanish recording with intermittent English. The purpose of six-profile diagnostic runs was to select one understandable, maintainable recognition strategy rather than ship multiple configurable decoding modes.

The same recording was tested without VAD and with Silero VAD:

| Approach | Observation |
| --- | --- |
| Default greedy decoding, no VAD | After otherwise plausible text, repeated `[HABLANDO EN INGLÉS]` roughly 1,200 times; substantial speech lost. About 185 seconds. |
| Strict fallback, no VAD (`entropy_thold=1.8`, `logprob_thold=-0.8`) | Most useful complete transcript, without catastrophic looping. About 236 seconds. Some English passages represented by markers or minor recognition errors. |
| Beam Search, no VAD | Substantial, largely complete transcript with fewer missing English passages, but possible language/translation errors and around 502 seconds. |
| Initial temperature 0.2, no VAD | Another substantial repetition loop, around 748 seconds. |
| No-speech threshold 0.4, no VAD | Did not materially improve the strict-fallback result. |
| VAD enabled | Prevented the earlier catastrophic loop but introduced many short repeated phrases; each run took about 31–38 minutes. Current VAD integration restarted recognition separately per speech region. |

These are qualitative comparisons of transcripts from the same audio, **not** word-error-rate benchmarks against a verified reference transcript. The failure-free result on this recording is not a guarantee against all omissions or hallucinations.

The first production run with the strict primary pass and full-file Beam fallback still showed a repeated phrase (e.g. `es una tirolina` 14 times). Whole-file retry allowed the native greedy decoder to waste time repeating speech before any correction could start, and a replacement transcript could omit entire sections even if its repetition count improved. This motivated **early local repair**, superseding the initial whole-file fallback decision below.

## Decision

- Maintain one user-facing automatic recognition flow; do not reintroduce VAD or six diagnostic modes.
- Keep hard-coded primary thresholds `entropy_thold=1.8` and `logprob_thold=-0.8`. Preserve user choices (model, language, task, prompt, threads, device).
- Decode the 16 kHz mono prepared WAV into samples once, retaining the loaded Whisper model. Process the remaining audio starting from its current sample offset rather than restarting the full file.
- Observe **native segment callbacks**, maintaining a rolling tail of text; a contiguous 3–32-word group repeated at least 3 times triggers immediate cancellation of the active greedy run. Keep a three-segment lookbehind uncommitted. On cancellation, asynchronously await native shutdown before constructing a new processor, preserving already accepted segments and current partial preview.
- Rerun at most 45 seconds **from the last confirmed segment boundary** using Beam Search. Append the repaired region and continue normal strict decoding from the end of the last Beam-recognized segment (or from the end of the window if none). Do not replace the complete transcript, or run Beam on the whole file during ordinary recovery.
- Limit local repairs to five; if exceeded, switch the remaining suffix to Beam once rather than permitting an unbounded greedy loop. If Beam fails for a bounded region, retry that region once with ordinary decoding and show a quality warning. Report repeated words still present in the bounded Beam result; do not silently delete transcription.
- Expose diagnostic lines prefixed `[WhisperDrop]` to stderr/terminal: duration, detection/resume audio offsets, repair counts, selected decoder, recovered segment counts, remaining loops, and elapsed time. Do not print entire audio paths or transcript contents.
- Preserve the raw Whisper transcript for optional AI correction. Detecting completely missing speech is outside the scope of this simple repetition guard.

## Alternatives Considered

- Always use Beam Search: improved some multilingual sections, but substantially slower without a clear overall advantage.
- Increase initial temperature or tighten no-speech threshold: did not resolve looping in the observed runs.
- Use VAD for every file: substantially slower and currently introduces short repeated phrases and context degradation at region boundaries.
- Full-file post-hoc Beam retry: rejected after the observed production run because it starts too late, is slow, may lose material and replaces good text outside the error region.
- Persistent VAD segmentation, multi-decode voting, alignment and complex overlapping-stitch heuristics: rejected as disproportionate to the immediate requirement.

## Consequences

- Ordinary transcripts are decoded with the strict settings only once; repeated segments trigger local recovery while the original decode is still in progress.
- The repair boundary is a native Whisper segment end; it is not a forced arbitrary splice in the middle of a segment. The three pending segments are withheld until safe, so the live preview cannot show removed repeated text in ordinary circumstances.
- A short repair window resets native context and can still cause minor boundary inaccuracies. A single native segment callback may not fire until a large span is decoded, so interruption is immediate **at callback granularity**, not at every token.
- Automatic restart is restricted to a bounded local window. A pathological recording can fall back to one Beam suffix after five repairs.
- Both decoding thresholds are implementation constants, not saved user settings.
- The heuristic cannot prove accuracy, detect nonrepeating hallucinations, or guarantee recovery of omitted audio. Continue surfacing errors as quality warnings rather than fabricating or silently deleting speech.
