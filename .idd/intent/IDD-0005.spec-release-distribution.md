# IDD-0005.spec-release-distribution

## Intent

ParakeetDrop is distributed as a ready-to-run desktop application through the existing GitHub repository's Releases. Windows x64 and macOS ARM64 and x64 are the required release platforms. A release version is defined by a Git tag in the form `vMAJOR.MINOR.PATCH`.

## Related Specifications

- IDD-0001 — Local desktop transcription
- IDD-0003 — Recognition and models
- IDD-0006 — About and application updates

## Behavior

- Normal CI runs restore, build, and tests on Windows, Linux, and macOS for pushes to `main`, pull requests targeting `main`, and manual dispatch.
- A developer starts the next patch release from a clean local checkout with `publish-next-version.bat`.
- The publish script fetches tags, switches to `main`, performs only a fast-forward pull, finds the latest valid release tag merged into `main`, increments PATCH, creates an annotated tag, and atomically pushes `main` plus the tag to `origin`.
- With no previous release tag, the first version is `v0.1.0`.
- A pushed `vMAJOR.MINOR.PATCH` tag starts the Release workflow.
- Release first verifies builds and tests and then creates required self-contained artifacts for:
  - Windows x64;
  - macOS Apple Silicon;
  - macOS Intel.
- Windows x64 is published as `ParakeetDrop-v{version}-win-x64.zip`, containing `ParakeetDrop.exe`, its managed application files, required bundled recognition-native resources, and the mandatory bundled FFmpeg shared libraries.
- macOS is published as `ParakeetDrop-v{version}-osx-arm64-app.zip` and `ParakeetDrop-v{version}-osx-x64-app.zip`, each containing `ParakeetDrop.app` and its architecture-specific native recognition and FFmpeg libraries.
- Release metadata inside the packaged application is derived from the tag and must match it.
- Release packages do not contain PDB files.
- Every package has a SHA-256 checksum; the release publishes the consolidated `SHA256SUMS.txt`.
- The repository and packaged archives include third-party notices for the exact FFmpeg/codec libraries, transcribe.cpp/ggml dependencies, and Parakeet Ultra weights, with the required licenses and attribution for the published artifacts.
- A repeated workflow run for the same tag updates the existing GitHub Release and replaces artifacts rather than creating a duplicate release.
- The release publishes only the three ParakeetDrop ZIPs and `SHA256SUMS.txt` as application artifacts.
- After a successful Release workflow, a separate Homebrew workflow updates `Casks/parakeetdrop.rb` in `main` with the release version and macOS artifact hashes.
- The Homebrew Cask token is `parakeetdrop`; it supports Apple Silicon and Intel and installs `ParakeetDrop.app`.
- Before the first release, the checked-in Cask is bootstrap metadata and is replaced by the Homebrew workflow.
- macOS packages are currently unsigned and not notarized.
- The Parakeet model is not embedded into releases; it remains an explicit application-managed download. The media-decoding and recognition runtimes are mandatory package content and are bundled app-locally.

## Distribution Contract

A macOS installation intended to support in-app automatic update uses this repository as a Homebrew tap and installs the Cask:

```text
brew tap dimonsmart/whisperdrop https://github.com/DimonSmart/WhisperDrop
brew install --cask dimonsmart/whisperdrop/parakeetdrop
```

The updater identifies that installation through the fully-qualified Cask name `dimonsmart/whisperdrop/parakeetdrop`.

## Durable Architecture And Constraints

- Git tag is the sole source of release version; publishing does not require a manual version edit in the project file.
- CI and release publication remain separate workflows.
- Release workflow must verify expected executables/app bundle, version metadata, required recognition-native assets and backends, required FFmpeg `avformat`/`avcodec`/`avutil`/`swresample` shared libraries, absence of FFmpeg/ffprobe and recognition CLI executables and PDB files, archive integrity, native dependency paths, and package checksums. Verification is performed against the final archived artifact, not only the pre-package publish directory.
- Release packaging must stay self-contained with respect to .NET, native recognition-runtime dependencies, and the pinned bundled FFmpeg media runtime. macOS verification rejects accidental `/opt/homebrew`, `/usr/local`, or system `libggml` dependencies.
- The existing repository, remote, GitHub Releases URL, and tag contract remain unchanged. The new application identity and Cask do not provide a legacy-installation, settings, model, or updater migration path.
- Signing/notarization may be added later without changing the tag/version contract.

## Acceptance Criteria

- A push/PR can be checked on Windows, Linux, and macOS through the Build workflow.
- `publish-next-version.bat` selects `v0.1.0` when no previous release exists and otherwise increments PATCH.
- A valid release tag publishes the three named ParakeetDrop artifacts and `SHA256SUMS.txt`.
- Packaged application version metadata equals the release tag version.
- Successful release publication updates the `parakeetdrop` Homebrew Cask metadata in `main`.
- Release artifacts remain usable without a separately installed .NET Runtime or FFmpeg. Windows x64 and both macOS architectures contain the media runtime inside the published artifact.

## Verification

- Unit/build CI runs without downloading multi-gigabyte recognition models.
- Release YAML validates tag shape and verifies package contents after final archive creation before GitHub Release publication, including media and recognition libraries, CLI exclusion, native dependency paths, third-party notices, and SHA-256 checksums.
- Homebrew workflow validates generated Cask Ruby syntax.
- End-to-end release is initiated explicitly by running `publish-next-version.bat`; implementation work itself does not create a release tag.
